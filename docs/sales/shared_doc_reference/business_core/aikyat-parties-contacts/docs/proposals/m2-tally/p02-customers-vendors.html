Proposal 2 · M2 Tally migration · 16 Oct 2026

How customers and vendors reach P&C

Today: the connector writes each customer and vendor into accounting.party — name, GSTIN, address, email, phone.

Proposal: the Tally connector calls the P&C API once for each customer or vendor ledger. P&C stores the party and returns a party_id. Accounting keeps only that party_id plus its own money fields. Running the migration again returns the same party_id — nothing is duplicated.

Agreed in the 15 Oct meeting (25:57–26:10): the connector may create parties in P&C. Names, PANs and GSTINs here are examples.

Step 3 · the API call

One call, safe to repeat

POST /api/v1/workspaces/{workspace_id}/parties Idempotency-Key: account:<ledger GUID> { "party_kind": "organization", "legal_name": "Brahmaputra Stationers Pvt Ltd", "identifiers": [ {"scheme": "IN_PAN", "value": "AABCB0000B"}, {"scheme": "IN_GST", "scope": "IN-AS", "value": "18AABCB0000B1Z2"} ], "standing": "supplier", "location": {"address": "...", "pincode": "781001"}, "email": "accounts@example.in", "phone": "+91 00000 00000", "source": {"book": "...", "ledger_guid": "..."} } → 201 {"party_id": "P-7", "result": "created"} → 200 {"party_id": "P-7", "result": "unchanged"} (re-run)
Who calls: the Tally connector, with its own service token.
The key is Accounting's own account key (account:<ledger GUID>). Same key → same party_id, every time.
The source (book + ledger GUID) is kept in P&C as evidence, so every party traces back to Tally.
Idempotency keys are already used by Accounting, Finance and Mail.
